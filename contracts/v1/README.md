# Контракт события · Budapest Signal

Версия документа **1.2**, снимок реализации **26 сентября 2026 года**.

Контракт собран по текущему коду и локальной базе сайта. Он описывает все поля события, фотографий, источников, хронологии и участников, а также правила формирования бэджей и силуэтов.

## Файлы и применение

| Файл | Назначение |
| --- | --- |
| [event-contract.ts](event-contract.ts) | Все типы TypeScript и фиксированные перечисления |
| [event-input.schema.json](event-input.schema.json) | Проверка одного события для заполнения, без внутренних ID |
| [event.schema.json](event.schema.json) | Проверка полного объекта события с ID |
| [event-input.example.json](event-input.example.json) | Заполненное событие из текущей базы, без внутренних ID |

| [participants.examples.json](participants.examples.json) | Синтетические варианты участников: ребёнок, неизвестный человек, группа, лидер |

| [context-claims.md](context-claims.md) | Сведения из СМИ, слова очевидцев и гипотезы с отдельным источником и степенью подтверждения |

`IncidentInput` — выделенный здесь формат для наполнения. `IncidentEvent` соответствует объекту, передаваемому интерфейсу. Сейчас сайт читает локальную БД: публичного API импорта, редактора и автоматической проверки этими схемами нет. Документ и схемы не меняют поведение сайта.

В таблицах «обязательно» относится к JSON-контракту. Неизвестные необязательные поля пропускаем, `null` не передаём. Пустой массив означает отсутствие сведений. Для неизвестного статуса участника есть явное значение `unknown`.

JSON Schema Draft 2020-12 дополнительно формализует требования к качеству заполнения: целые положительные ID и численность, целый неотрицательный возраст, диапазоны координат, даты со смещением, двухбуквенный код страны. Текущие TypeScript-типы и БД не обеспечивают все эти ограничения. Схемы запрещают неизвестные поля. Даты проверяются валидатором с включённой проверкой `format`. Строковые поля допускают пустую строку, как в текущей модели; для содержательного наполнения используйте осмысленный текст. URL остаются строками, проверка доступности ссылок в схемы не входит.

## 1. Основные поля события

| Поле | Тип | Обязательно | Что заполнять / где используется |
| --- | --- | --- | --- |
| `id` | integer | Только в полном объекте | Внутренний ID, создаётся БД |
| `slug` | string | Да | Уникальный постоянный ключ события; выбор события в интерфейсе |
| `title` | string | Да | Заголовок статьи, списка и подписи поверх первого фото; участвует в вычислении бэджей |
| `category` | string | Да | Категория исходных данных; участвует в вычислении типа события. **Не enum** |
| `status` | string | Да | Текстовый статус события и его бэдж, например «Подозреваемый задержан». **Не enum** |
| `verification` | string | Да | Текст о подтверждении сведений, показанный бэджем. **Не enum** |
| `district` | string | Да | Район, например «IX район». Свободный текст |
| `locationLabel` | string | Да | Читаемое место / адрес; также поверх фото |
| `locationPrecision` | string | Да | Пояснение точности места. Свободный текст, не enum |
| `latitude` | number | Да | Широта маркера, от −90 до 90 |
| `longitude` | number | Да | Долгота маркера, от −180 до 180 |
| `occurredAt` | string, date-time | Да | Время происшествия: сортировка и фильтры периода |
| `summary` | string | Да | Описание происшествия; также участвует в вычислении бэджей |
| `updatedAt` | string, date-time | Да | Время последнего обновления события; задаётся данными |
| `sources` | `IncidentSource[]` | Да | Источники публикаций, можно `[]` |
| `updates` | `IncidentUpdate[]` | Да | Хронология событий, можно `[]` |
| `media` | `IncidentMedia[]` | Да | Фотографии, можно `[]` |
| `participants` | `Participant[]` | Нет | Участники. Для нового наполнения рекомендуется всегда передавать массив, хотя текущий UI допускает отсутствие |
| `context` | `ContextClaim[]` | Нет | Сведения и версии о событии или конкретном участнике; каждое со своим источником и степенью подтверждения. [Поля и правила](context-claims.md) |

В формате для наполнения вложенные `sources`, `updates`, `media` используют соответствующие типы `…Input`, без `id` и `incidentId`. Числа передаются числами, не строками. Даты: например `2026-09-21T14:30:00+02:00` или `2026-09-21T12:30:00Z`. Интерфейс показывает их на русском в часовом поясе `Europe/Budapest`. Рекомендуется единообразное хранение времени в UTC: текущая БД сортирует строковые даты.

`category`, `status`, `verification`, `district`, `locationPrecision`, `sourceType` сейчас **не имеют закрытого списка значений**. Примеры текста в этом документе не ограничивают допустимый словарь.

## 2. Источники — `sources[]`

| Поле | Тип | Обязательно | Смысл |
| --- | --- | --- | --- |
| `id` | integer | Только полный объект | ID записи источника |
| `incidentId` | integer | Нет | Связь с событием: присутствует в строке БД, UI её не требует |
| `sourceType` | string | Да | Тип источника, например «Официальный источник»; определяет оформление бэджа |
| `outlet` | string | Да | Название издания / ведомства |
| `sourceUrl` | string | Да | Ссылка на исходную публикацию; рекомендуется абсолютный HTTP(S) URL |
| `publishedAt` | string, date-time | Да | Дата публикации источника |
| `note` | string | Да | Пояснение, что сообщает или подтверждает источник |

Показ от новых источников к старым по `publishedAt`. В БД `sourceUrl` уникален **во всей таблице**, включая другие события.

## 3. Хронология — `updates[]`

| Поле | Тип | Обязательно | Смысл |
| --- | --- | --- | --- |
| `id` | integer | Только полный объект | ID записи хронологии |
| `incidentId` | integer | Нет | Связь с событием, как у источника |
| `publishedAt` | string, date-time | Да | Дата пункта хронологии |
| `title` | string | Да | Короткий заголовок изменения |
| `detail` | string | Да | Подробности изменения |
| `verification` | string | Да | Метка подтверждения / источника; свободный текст |

Показ от старых записей к новым. Внутри одного события сочетание `publishedAt` + `title` уникально. У пункта хронологии нет собственного `sourceUrl`, списка фотографий или участников. Его сигнальные бэджи вычисляются по `title` + `detail`.

## 4. Фотографии — `media[]`

| Поле | Тип | Обязательно | Смысл |
| --- | --- | --- | --- |
| `id` | integer | Только полный объект | ID фотографии |
| `incidentId` | integer | Нет | Связь с событием |
| `imageUrl` | string | Да | Ссылка на изображение или локальный путь от корня сайта, например `/images/example.jpg` |
| `sourceUrl` | string | Да | Оригинальная публикация фотографии |
| `outlet` | string | Да | Издание / источник фото |
| `credit` | string | Да | Авторство / подпись правообладателя |
| `caption` | string | Да | Подпись под фото и текст `alt` |
| `isSensitive` | boolean | Да | `true`: фотография сначала размыта, открывается нажатием; `false`: видна сразу |

БД по умолчанию ставит `isSensitive = false`, но в JSON передаём значение явно. `imageUrl` уникален во всей таблице фотографий.

Фотографий может быть несколько. Сервер сортирует их по `id` по возрастанию: **первая становится ведущей**. Отдельных полей `coverImageId`, `isCover`, `sortOrder` нет. На десктопе галерея находится наверху блока, заголовок и адрес — на первом фото с полупрозрачным тёмным размытым фоном, бэджи — ниже. На мобильном используется обычное расположение галереи после описания. Заголовок «Фото» отсутствует. Без фотографий показывается обычный заголовок события.

## 5. Участники — `participants[]`

| Поле | Тип | Обязательно | Смысл |
| --- | --- | --- | --- |
| `key` | string | Да | Стабильный ключ участника, уникальный внутри события |
| `role` | `ParticipantRole` | Да | Роль: подозреваемый, потерпевший, осуждённый, другой участник |
| `label` | string | Да | Подпись карточки, например «Водитель автомобиля»; используется, если нет имени |
| `status` | `ParticipantStatus` | Да | Текущий статус, определяющий текст, цвет и иконку бэджа |
| `profile` | `PersonProfile \| GroupProfile` | Да | Один человек или группа; выбор по `kind` |
| `note` | string | Нет | Дополнительные известные сведения |
| `sourceUrl` | string | Да | Публикация, подтверждающая сведения об участнике |
| `sourceLabel` | string | Да | Подпись ссылки на источник |
| `asOf` | string, date-time | Да | Дата актуальности сведений об участнике |

Карточки разделяются по `role` в порядке: подозреваемые → потерпевшие → осуждённые → другие участники. Внутри роли сохраняется порядок исходного массива. Пустой список показывает «Сведения об участниках пока не опубликованы».

### Роли — `ParticipantRole`

| Значение | Раздел интерфейса |
| --- | --- |
| `suspect` | Подозреваемые |
| `victim` | Потерпевшие |
| `convicted` | Осуждённые |
| `involved` | Другие участники |

Роль и статус — разные поля. Например, `role: "victim"` + `status: "injured"`. Автоматической проверки допустимых сочетаний сейчас нет. Роль осуждённого заполняется по сведениям источника; подозрение само по себе не означает осуждение.

### Статусы — `ParticipantStatus`

| Значение | Базовый текст | Цвет | Иконка |
| --- | --- | --- | --- |
| `detained` | Задержан | Приглушённый зелёный | Наручники |
| `wanted` | В розыске | Красный | Нет отдельной |
| `in-custody` | Под стражей | Приглушённый зелёный | Наручники |
| `charged` | Предъявлено обвинение | Приглушённый зелёный | Нет отдельной |
| `convicted` | Осуждён | Красный | Нет отдельной |
| `released` | Освобождён | Приглушённый зелёный | Нет отдельной |
| `deceased` | Погиб | Красный | Череп |
| `injured` | Пострадал | Жёлтый | Медицинский крест |
| `unknown` | Статус не указан | Приглушённый зелёный | Нет отдельной |

Для `detained`, `convicted`, `released`, `deceased`, `injured` текст согласуется с женским полом или группой: «Задержана», «Погибли» и т. п. Цвет и иконку вручную передавать не нужно.

### Человек — `PersonProfile`

| Поле | Тип | Обязательно | Смысл |
| --- | --- | --- | --- |
| `kind` | literal `"person"` | Да | Переключатель типа профиля |
| `name` | string | Нет | Известное опубликованное имя; заменяет `label` в заголовке |
| `gender` | `"male" \| "female"` | Нет | Мужской / женский пол. Неизвестен — поле отсутствует |
| `age` | integer ≥ 0 | Нет | Точный возраст в полных годах |
| `ageGroup` | `"child" \| "adult" \| "older"` | Нет | Возрастная группа, если точный возраст неизвестен |
| `citizenship` | object | Нет | Сведения о гражданстве, если опубликованы |
| `citizenship.code` | string | Если есть объект | Две заглавные латинские буквы кода страны, например `HU`; из них формируется флаг |
| `citizenship.name` | string | Если есть объект | Название страны, например «Венгрия» |

`child` — до 18 лет, `adult` — 18–59, `older` — от 60. Если передан `age`, он имеет приоритет над `ageGroup`. Не передавайте противоречивые значения. `ageGroup` управляет силуэтом; без точного `age` текст карточки всё равно говорит «Возраст не указан».

Поле `citizenship` означает **гражданство**, а не этническую принадлежность или место рождения. Страна не выводится из места происшествия, имени или внешности. Для неизвестных значений не используем пустые объекты и условные коды `XX`: пропускаем поле. Текущая функция флага проверяет только две заглавные буквы, не существование страны.

### Группа — `GroupProfile`

| Поле | Тип | Обязательно | Смысл |
| --- | --- | --- | --- |
| `kind` | literal `"group"` | Да | Группа участников |
| `count` | integer ≥ 1 | Нет | Общая численность, включая лидера |
| `gender` | `"male" \| "female"` | Нет | Общий пол, только если это известно обо всей группе. Для смешанной / неизвестной группы поле пропускается |
| `leader` | object | Нет | Один предполагаемый лидер |
| `leader.person` | `PersonProfile` | Если есть лидер | Профиль лидера, включая известные возраст и гражданство |
| `leader.status` | `ParticipantStatus` | Если есть лидер | Собственный статус лидера |
| `leader.sourceUrl` | string | Если есть лидер | Источник сведений о лидере |

Правила количества:

- **1–4 человека:** известная численность разворачивается в отдельные карточки. Когда известны индивидуальные данные, лучше сразу заполнять отдельные `person`-записи.
- **5 и более:** явная `group`-запись показывается общей карточкой с групповым силуэтом и счётчиком. Лидер может быть выделен внутри неё и входит в `count`.
- **Численность неизвестна:** одна запись с нейтральным силуэтом и текстом «Численность уточняется»; приложение не создаёт вымышленных людей. Это текущее исключение для неполных данных, а не подтверждение группы от пяти.

Пять самостоятельных `person`-записей автоматически в группу не объединяются. У группы нет общего возраста, гражданства или массива `members`. Если внутри неё разные роли или статусы, для точного описания нужны отдельные записи.

При разворачивании малой группы лидер становится первым человеком; остальные наследуют общий пол и статус. Их ключи формируются как `<key>-person-1`, `<key>-person-2` и т. д. Индивидуальные имена и возраст не придумываются. Исходное групповое `note` заменяется подписью «Индивидуальные сведения не опубликованы», у лидера — «Предполагаемый лидер». Лидер получает собственный источник и статус, остальные — общие; `asOf` остаётся общим. Отдельной истории статусов участников сейчас нет.

## 6. Силуэты: вычисляются из профиля

| Условие | Логический вариант |
| --- | --- |
| Известный мужчина, взрослый / возраст не указан | `adult-male` |
| Известная женщина, взрослая / возраст не указан | `adult-female` |
| Мужчина от 60 лет / `older` | `elderly-male` |
| Женщина от 60 лет / `older` | `elderly-female` |
| Мальчик до 18 лет / `child` | `boy` |
| Девочка до 18 лет / `child` | `girl` |
| Ребёнок, пол не указан | `child-neutral` |
| Пол не указан, остальные случаи | `person-neutral` |
| Группа с известной численностью от 5 | `group` |

Неизвестный пол даёт нейтральный силуэт без отличительных черт, в том числе при известном пожилом возрасте. Взрослый силуэт при неизвестном возрасте — оформление, а не утверждение о возрасте. Это условные изображения, не реальные портреты людей. Текущая версия нейтральных силуэтов без знака вопроса.

Файлы находятся в `/avatars/profile/`. Для `elderly-male`, `person-neutral`, `child-neutral` используются имена с суффиксом `-refined.png`, для остальных — `<вариант>.png`. Отдельных полей `avatarUrl`, `avatarType`, `portrait` у участника нет.

## 7. Все бэджи события

Событие хранит текстовые `status` и `verification`, они показываются как бэджи. Тип происшествия и сигнальные иконки вычисляются из текста. Массива `badges` во входных данных **нет**.

### Тип происшествия

Проверяется строка `title + category + summary`, приведённая к нижнему регистру. Выбирается первое совпадение по порядку:

| Приоритет | Фрагменты / регулярное выражение | Бэдж | Иконка |
| --- | --- | --- | --- |
| 1 | `дтп\|столкнов\|авари` | ДТП | Автомобиль |
| 2 | `драк` | Драка | Скрещённые мечи |
| 3 | `ограб\|грабёж\|грабеж\|краж` | Ограбление | Кошелёк |
| 4 | `несчастн\|падени\|утонул\|отравлен` | Несчастный случай | Предупреждающий треугольник |
| 5 | `нападен\|насиль\|убийств\|избил\|побои` | Нападение | Нож |
| 6 | Нет совпадений | Происшествие | Щит |

Это шесть **вычисляемых значений**, а не enum входного поля `category`. Например, кража сейчас тоже приводит к отображаемому типу «Ограбление».

### Сигнальные иконки

Проверяется строка `title + status + summary` в нижнем регистре:

| Вычисляемое значение | Условие | Подпись | Вид |
| --- | --- | --- | --- |
| `death` | `смерт\|погиб\|умер\|убийств` | Есть погибшие | Красный, череп |
| `suspect-wanted` | `разыскив` | Подозреваемый разыскивается | Приглушённый зелёный, лупа |
| `suspect-detained` | `задерж\|под страж\|арестован`, если нет совпадения розыска | Подозреваемый задержан | Приглушённый зелёный, наручники |

`death` может сочетаться с одной из двух других иконок. Розыск имеет приоритет над задержанием. У пункта хронологии тот же алгоритм, но текст берётся из `title + detail`. Отдельного сигнала «есть пострадавшие» на уровне события пока нет; жёлтый крест есть у участника со статусом `injured`.

**Ограничение текущей реализации:** верхние сигналы не вычисляются из `participants`. Изменение статуса человека само по себе их не меняет. Алгоритм ищет фрагменты слов и не понимает отрицания: фраза «погибших нет» тоже может дать красную иконку. Это зафиксированное поведение, не предлагаемое правило проверки фактов.

### Официальность источника и хронологии

У источника анализируется `sourceType`, у пункта хронологии — `verification`. Значение считается официальным, если содержит `официаль`, `police` или `brfk` без учёта регистра и при этом **не** содержит `неофициаль`. Остальные значения получают неофициальное оформление. Например, «Официальный источник» / «Неофициальная информация» — свободный текст, не enum. Числовой оценки достоверности нет.

## 8. Хранение, уникальность и порядок

| Объект | Таблица | Связь / ограничение |
| --- | --- | --- |
| Событие | `incidents` | `id` — PK, `slug` — уникальный |
| Источник | `incident_sources` | `incident_id` → событие; `source_url` глобально уникален |
| Хронология | `incident_updates` | `incident_id` → событие; уникально сочетание события, даты и заголовка |
| Фотография | `incident_media` | `incident_id` → событие; `image_url` глобально уникален |
| Участник | `incident_participants` | `id` — PK; `incident_id`; `participant_key`; `details` — JSON объекта `Participant` |
| Сведения и версии | `incident_context` | `id` — PK; `incident_id`; `claim_key`; `details` — JSON объекта `ContextClaim`; ключ уникален внутри события |

Имена в JSON — `camelCase`, столбцы БД — `snake_case`: например `locationLabel` → `location_label`, `isSensitive` → `is_sensitive`. В SQLite `is_sensitive` хранится как 0/1, наружу передаётся `boolean`. Все ID таблиц создаются автоматически.

Участник в JSON не содержит ID строки БД. Его `key` должен совпадать с `participant_key`; пара `incident_id + participant_key` уникальна. Сейчас JSON участника читается без полноценной проверки структуры во время выполнения.

События сортируются по `occurredAt` от новых к старым, источники — по `publishedAt` от новых к старым, хронология — по `publishedAt` от старых к новым, фотографии и участники — по ID строки от меньшего к большему. Схема отдельного JSON не проверяет уникальность между событиями, равенство `incidentId` родительскому `id` и уникальность `participants[].key`: эти правила нужно соблюдать при сохранении.

## 9. Что не является полем события

Период фильтра, выбранная карточка, тема день/ночь, раскрытие чувствительного фото и состояние карты — состояние интерфейса. Цвет маркера зависит от темы и выбора, а не от тяжести происшествия.

Сейчас нет отдельных полей для видео, тяжести, числа погибших/пострадавших, произвольных бэджей, числовой достоверности, этнической принадлежности, истории статусов участника или ручного выбора его силуэта. При необходимости это будет расширение контракта.

Мотив, гражданство по версии источника, занятия, пребывание в городе и жилищная ситуация теперь поддерживаются как отдельные атрибутированные `context`-утверждения. Они не переписывают автоматически основные сведения профиля и не управляют его флагом или силуэтом.

Фильтры сайта: 24 часа, 7 дней, 31 день. В текущей демонстрационной версии точка отсчёта зафиксирована на `2026-09-25T00:00:00+02:00`: новые данные за её пределами могут не попасть в выбранный период. Это настройка реализации, не свойство события.
